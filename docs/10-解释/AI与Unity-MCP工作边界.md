# AI、Unity CLI 与 Unity MCP 工作边界

## AI 负责

- 将自然语言需求转换为视觉目标和技术约束。
- 拆解形状、运动、材质、颜色、节奏和空间层次。
- 选择 Particle System、VFX Graph、Shader、Mesh、Trail、Timeline 等技术。
- 制定层级结构、参数表和制作顺序。
- 根据运行结果提出有依据的迭代修改。
- 记录参数、失败原因、性能数据和可复用经验。

## Unity CLI 负责默认执行层

本工程默认使用 Unity 官方 CLI 完成：

- Unity Editor 版本和模块查询、安装与选择。
- 项目创建、打开、结构检查和版本管理。
- 认证、环境诊断和许可证状态检查。
- 构建、测试、批处理命令和日志收集。
- 执行项目注册的 `[CliCommand]`、`eval` 和 `eval_file` 命令。

CLI 是自动化工作的首选入口。能由 CLI 完成的操作，不再优先通过 MCP 绕行。

## Unity MCP 负责补充

Unity MCP 是 AI 与正在运行的 Unity Editor 之间的实时桥接，适合 CLI 没有覆盖的操作：

- 查询实时场景、层级、对象、组件和资源。
- 创建、复制、删除和修改 GameObject。
- 设置 Transform、材质、粒子和 VFX 参数。
- 读取 Console、运行状态和截图。
- 操作需要 Editor 实时上下文的资源和菜单。

使用 MCP 前必须记录为什么 CLI 不足，并验证 MCP 的真实能力。MCP 不是 Unity CLI 的替代品，也不能绕过 Editor license、项目错误或人工授权。

## Unity 工程负责

Unity 提供运行环境、渲染管线、资源序列化、性能分析和最终效果验证。CLI 或 MCP 命令执行成功，不等于效果已经完成；必须确认项目实际运行、资源保存和结果可复现。

## 人工判断负责

人工仍需要确认：

- 视觉目标是否符合需求。
- 特效是否有风格一致性。
- 运行结果是否达到质量要求。
- 性能限制和平台目标是否合理。
- 哪些方案值得沉淀为通用资产。

## 智能工具选择顺序

1. 先检查任务类型和目标 Unity 工程。
2. 项目检查、Editor 管理、构建、测试、认证和注册命令优先用 CLI。
3. 需要实时层级或 Editor 状态时，再用 MCP。
4. 执行前读取版本、路径、认证和可逆性。
5. 执行后读取退出码、日志、项目状态和产物。
6. 只有真实运行结果和证据满足标准，才把实验从 `planned`/`experimental` 推进到 `verified`。

## 工作原则

1. CLI 是默认执行层，MCP 是有记录的补充层。
2. 工具操作成功不等于视觉质量达标。
3. 所有重要修改都要通过运行结果验证。
4. 自动化优先操作可重复、可检查的参数。
5. 复杂资产可结合 CLI、Editor 脚本、MCP 和预制资源。
6. 任何能力限制、授权问题和失败日志都必须记录。
