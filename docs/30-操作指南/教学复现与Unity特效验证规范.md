## 阶段 2：跑通 Unity 特效播放截图工具

### 目标

建立能够按请求播放时间采集真实 Unity Game View 的工具链，避免固定等待或偶然截图错过短生命周期特效。

### 流程

```text
确认连接工程和 Unity 版本
  -> 确认场景、特效对象和相机
  -> 确认 Editor 状态为 playing
  -> 重置目标粒子系统
  -> Simulate(requestedTime)
  -> capture_game_view
  -> 检查 PNG 和连续帧
  -> 写入 capture manifest
```

### 已验证规则

- Unity CLI 优先用于项目检查、状态检查和截图调用。
- 截图使用真实 Game View，不用静态 Scene View 代替运行画面。
- `playOnAwake=false` 的粒子系统必须显式触发。
- 短特效不能依赖命令往返和 `sleep` 捕获峰值。
- 确定性采样使用 `Stop(...StopEmittingAndClear)` 后 `Simulate(requestedTime)`。
- 静态 Mesh 和动态 ParticleSystem 必须分别记录，不能把静态主体误判为完整动态。
- 截图工具通过不等于特效视觉通过。

### 视觉可见性标准（强制）

所有参考帧、Unity Game View 截图、候选贴图和对比图，必须先通过本标准，才能写入人工视觉结论或驱动下一轮参数修改。

#### 可见性成立条件

以下三项必须同时满足：

1. **展示通道成功**：通过已实际工作的图像展示通道打开目标 PNG/JPG 或标准化本地复核页；不是只读取文件路径、元数据、PIL 统计或 HTTP 状态。
2. **画面内容可描述**：当前会话能够直接确认画面中的主体轮廓、方向、占屏、背景关系、颜色层次和时间状态中的至少必要字段；不能只确认“图片存在”或“像素有变化”。
3. **证据可追溯**：记录展示的文件相对路径、来源/时间点、尺寸、SHA-256 或 manifest 条目，以及展示通道和复核时间。

三项缺一不可。只有文件存在、PNG 可解码、文件大小变化、相邻帧有像素差异、浏览器返回 200、Unity 命令成功或截图路径正确，均不算“已看到”。

#### 展示通道优先级

按以下顺序尝试，并在记录中写明实际成功的通道：

1. 本地标准化 PNG/JPG 通过当前会话的原生图像展示能力直接呈现；
2. 本地复核服务只提供已经生成的标准化 PNG/JPG，浏览器打开复核页并实际呈现画面；
3. Unity Game View 截图通过可见的浏览器/图像展示通道打开，不能以 Unity CLI 返回值替代；
4. 若以上通道均不可用，只能保留机器检查和文件证据，状态写为 `blocked_environment`，禁止写入视觉语义结论、禁止据此宣称通过。

展示通道偶发成功不能视为稳定成功。每次新任务开始、切换来源或切换工程后，必须用一张已知 PNG 做可见性 smoke test；连续参考或 Unity 截图复核前，还要成功打开至少起势、峰值和收束三个时间点。

#### 视觉复核记录

人工复核必须绑定：

```text
source_or_scene
relative_path
requested_time_or_video_time
display_channel
visible_observations
confidence
reviewed_at
```

`visible_observations` 至少包含当前目标所需的轮廓、方向、占屏、层次或时序字段。看不到时不要猜测，改记为 `not_visible` 并保留错误文本。

#### Unity 截图的取景门禁

Unity 截图前必须确认：

- 目标场景、目标对象和唯一目标相机已通过层级或 GlobalObjectId 确认；
- additive 场景中不能存在多个同名或同标签的候选相机；若存在，截图命令必须使用唯一对象引用，不得按模糊名称选择；
- 截图 manifest 记录相机对象、场景、请求时间和实际保存文件；
- smoke test 和连续时间点截图都由同一相机、同一分辨率和同一渲染设置产生。

发现重复相机、场景来源不明、展示宿主未附着或图片内容未返回时，视觉状态立即降为 `blocked_environment`，先修复取景/展示链路，再继续视觉迭代。

#### 禁止的替代结论

以下表述不能作为人工视觉结论：

- “图片路径正确，所以看到了”；
- “平均亮度/边缘密度说明画面应该是某种效果”；
- “相邻帧不同，所以节奏正确”；
- “Shader、材质、Prefab 或 ParticleSystem 配置成功，所以效果落位”；
- “浏览器页面加载成功，所以已经完成视觉复核”。

客观统计可以用于排序、异常定位和回归检查，但必须明确标记为 `machine_assisted`，不能替代人工视觉门禁。

### 子步骤 3.3：ParticleSystem 参数表

每个 ParticleSystem 必须记录完整可复现参数：

- Duration、Loop、Start Delay、Start Lifetime。
- Start Speed、3D Start Size、Start Rotation。

- Shape 类型、角度、半径、Mesh 和方向。
- Simulation Space、Scaling Mode、Gravity。
- Size over Lifetime、Color over Lifetime、Rotation over Lifetime。
- Noise、Collision、Trails、Sub Emitters。

参数记录不能只写“少量粒子”“快速消失”或“颜色偏橙”等主观描述，必须保留 Unity Inspector 可回读的数值或明确的曲线关键点。

### 子步骤 3.4：材质、Shader 和纹理表

每个材质必须记录：

- 材质名称和所属层。
- Shader 名称和 Unity/URP 版本。
- Blend、Cull、ZWrite、ZTest、Render Queue。
- Base Map、Mask/Dissolve Map、Spark/Noise/Flow Map。
- Emission、颜色、透明度和边缘高亮参数。
- UV 方向、速度、平铺、Offset 和溶解推进方式。
- 每张纹理的来源、路径、尺寸、通道含义、导入设置和授权状态。

材质和纹理必须与层职责对应。不能只把一张不确定用途的贴图绑定到所有层，再用颜色和 Bloom 假装完成材质层次。

### 子步骤 3.5：结构复现与逐层对比

复现顺序为：

1. 先按层级结构建立对象和组件。
2. 先用稳定的纯色或最小材质验证主体轮廓和层职责。
3. 对每个层单独开关并截图，确认它确实承担预期作用。
4. 按阶段 2 的确定性截图工具采集起势、主体、峰值和收束。
5. 将 Unity 连续截图与教程联系表逐时间点对比。
6. 再逐层加入真实材质、Shader、纹理、运动和溶解。
7. 每次只改变一类问题，并记录修改前后差异。

## 阶段 4：引擎制作

状态：进行中；当前从第 1 步资产准备开始。

阶段 4 的目标是把阶段 3 的学习结果变成一个可运行、可逐层检查、可与参考视频连续对比的 Unity 特效。引擎制作分为三个有顺序的步骤：资产准备、Unity 层级骨架与参数填入、对比和微调。

### 第 1 步：资产准备

资产准备不是最后补资源，而是把学习教程时识别出的资产需求落实为可检查清单。至少包括：

- Shader：主体、暗底、快速打击、亮边、溶解和地面反馈所需的功能 Shader；无法确认教程原 Shader 时，标记为本项目复刻实现。
- 材质：按层职责建立独立材质，记录 Blend、Emission、Mask、UV 和溶解参数。
- 贴图纹理：主体刀光贴图、简单快速打击贴图、Mask/Dissolve、内部纹理/Flow、地面反馈贴图；每张纹理记录来源、路径、尺寸、通道、导入设置和授权状态。
- 模型：主体平面或刀光 Mesh，记录 Pivot、轴向、UV、细分和是否支持点位变形。
- 其他依赖：Bloom、点光、地面承载平面、脚本或 Timeline 触发依赖。

第 1 步输入是教程学习手册、当前资源库和工程版本；输出是资产清单、授权与格式检查结果、Shader/材质/贴图/模型占位或已确认资产，以及尚缺资产列表。资产进入 Unity 前必须检查来源、SHA-256、授权状态、格式兼容性和导入设置；资源库中存在不等于可以公开分发或直接适用。

第 1 步验收证据：资产清单文件、每项资产的用途和所属层、材质与 Shader 引用关系、纹理导入检查、缺失项说明，以及必要的资源索引或截图记录。没有完成这些记录，不进入正式层级制作。

### 第 2 步：Unity 层级骨架、粒子参数和资产填入

先在目标 Unity `6000.5.9f1`、URP `17.5.0` 工程中建立可逐层开关的骨架，再填入资产和参数。建议的第一版职责骨架为：

```text
BladeRoot
  CoreBody
  DarkBase
  FastStrike_A
  FastStrike_B
  EdgeHighlight
  InternalDetail
  Atmosphere
  HitPoint
  GroundFeedback
  Residual
```

实际对象类型和数量必须以工程回读为准；此结构是可执行映射，不冒充教程原始 Hierarchy。每层需要记录 GameObject、ParticleSystem/MeshRenderer/Light 等组件数量、资产引用、Simulation Space、生命周期、尺寸、颜色、Emission、Shape、Size/Color over Lifetime、Custom Data、Renderer 和排序关系。

这一步包含三个同步目标：

- 形体：先让主体 Mesh/粒子承载的轮廓、轴向、宽度、尖端和变形成立；
- 颜色：按主色、辅助色、点缀色职责填入材质和粒子颜色，避免一开始用 Bloom 覆盖形体问题；
- 节奏：调整主体进入、命中峰值、快速打击层延迟、暗层慢退和残留收束。

第 2 步验收证据：Unity 层级截图或可回读记录、每层参数表、材质和纹理引用、逐层开关截图、确定性播放截图 manifest，以及起势、主体、峰值和收束时间点的连续画面。编译成功、Prefab 存在或 PNG 文件存在都不能单独作为通过条件。

### 第 3 步：参考对比和微调

第 2 步能运行不等于视觉成立。第 3 步必须反复对比本项目播放结果与参考视频，定位“刀光落了”的具体原因，再只修改一类问题。重点检查：

- 形体：轮廓、尖端、宽度变化、弧线方向、空间朝向和是否有拉伸/漂浮；
- 节奏：起势是否太慢、命中峰值是否错位、快速层是否过早铺满、收束是否拖沓；
- 材质：主体是否清晰、暗底是否发灰、亮边是否吞细节、Mask/UV/溶解方向是否正确；
- 层次：主体、支撑、内部纹理、氛围、命中点和地面反馈是否各司其职；
- 场景关系：命中位置、地面方向、点光范围、镜头占屏和后处理强度是否服务主体。

本步骤调用已有审美积累进行评估，包括快入慢出、颜色职责、方向性溶解、支撑层与冲击层时序、冲击层与地面反馈权重等知识卡片。审美卡片用于提出可解释的判断规则，不替代参考视频和连续 Unity 截图。

每轮记录：参考时间点、Unity 请求时间、问题描述、唯一修改变量、修改前后参数、截图 manifest、人工视觉判断、副作用、是否保留和下一轮结论。推荐微调顺序为：形体 -> 节奏 -> 材质 -> 层次 -> 冲击反馈 -> 场景融合 -> 性能；不得同时修改相机、模型、Shader、粒子和后处理后再下结论。

第 3 步暂不等同于阶段 5 成功样本验收。只有连续播放和工程证据共同通过，才可进入阶段 5。

### 成功样本门禁

只有同时满足以下条件，才能把效果标记为成功样本：

- 人工确认画面质量和参考目标一致到可接受程度。
- 连续播放中的形体和动态成立，不只是单帧好看。
- 主体轮廓、颜色、材质层级和冲击反馈均可解释。
- Unity 场景、Prefab、Timeline 和材质引用可重复运行。
- 截图、参数、日志、失败方案和复验结果齐全。
- 没有把工具成功、文件存在或像素变化冒充视觉完成。
