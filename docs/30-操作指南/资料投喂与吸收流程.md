# 资料投喂与吸收流程

## 流程总览

```text
登记 → 筛选 → 切片 → 提取 → 投喂 → 建卡 → 实验 → 验证 → 沉淀 → 复核
```

资料进入 `knowledge/inbox/` 后，按以下步骤推进。每一步完成后更新状态和索引。

## 1. 登记

### 输入

用户提供的文件、链接、源工程、视频、文章或自主检索结果。

### 操作

创建 `SRC-*` 资料卡，记录标题、来源、作者、平台、获取日期、授权、版本、类型和关联需求。

常见文档可以先用统一导入入口转换到 `knowledge/inbox/`：

```bash
python -m workspace.tools.media_integrations_cli import-document \
  "<document_path>" --knowledge-root knowledge
```

转换只是格式整理，不代表资料已经筛选或可信；仍需登记来源、授权、版本和适用范围。

### 输出

资料登记记录和原始引用路径。

### 通过条件

能够回答“资料是什么、来自哪里、何时获得、能否使用”。未知字段明确标记，不用猜测补齐。

## 2. 筛选

检查来源可靠性、授权状态、文件完整性、恶意或无关内容、Unity 版本、渲染管线和外部依赖。

源文件要先确认是否能在隔离环境打开；视频要确认是否完整、有声音或字幕；文章要确认正文和图片是否可读。

### 输出

筛选结论、风险说明和 `screened` 状态，或标记为隔离/拒收。

## 3. 切片

按资料类型拆分为可处理单元，并为视频建立视觉证据：

- 源文件：按场景、Prefab、材质、Shader、VFX Graph、脚本和纹理依赖切分。
- 视频：按时间戳切分目标、准备、制作、调参、修正和总结；先用统一媒体工具读取 `media_meta.json`，可用 PySceneDetect 生成场景边界候选，再生成代表性帧、修改前后帧和关键动态片段。
- 文章：按问题、方案、步骤、参数、限制和参考资料切分。
- 图片：记录画面区域、视觉层次、颜色和运动假设；图片本身不是技术证据。

视频抽帧至少覆盖：

1. 最终效果或案例全貌。
2. 讲解问题时的画面。
3. 修改前和修改后。
4. 爆发、持续和收尾等动态关键点。
5. Inspector、Shader Graph、VFX Graph 或节点画面（视频确实展示时）。

### 输出

`knowledge/sources/` 下的切片、时间戳、截图、文件路径或章节索引。

## 4. 提取

把切片内容分成四类，并将语音与画面对照：

- 事实：资料明确展示或说明的内容。
- 步骤：可以照着执行的操作。
- 假设：根据现象推断但尚未验证的原因。
- 限制：版本、依赖、性能、授权或适用范围限制。

对视频额外记录：

- 画面中实际出现的对象、形状、材质、颜色和层次。
- 动画或效果的出现顺序、速度、爆发、衰减和收尾。
- 修改前后是否真的发生可见变化。
- 画面与作者口述是否一致，是否存在“说法正确但画面未展示”的部分。
- 视觉证据文件路径和截图时间点。

不要把作者的经验判断改写成无条件的普遍结论，也不要把字幕中猜出的术语当成画面事实。

## 5. 创建投喂任务

使用[投喂任务模板](../90-模板/投喂任务模板.md)，明确本次只解决什么问题，需要什么输出，以及禁止模型臆测哪些内容。

视频任务必须明确是否需要：

- 只做语音/字幕初步索引。
- 抽取画面和效果证据。
- 对照修改前后。
- 分析动态节奏或局部慢放。
- 读取画面中的 Unity 工程操作。

投喂任务应尽量小，例如“提取该视频中冲击波的时间结构和材质参数，并保存前后对照帧”，而不是“学习这个视频的全部内容”。

## 6. 建立知识卡片

使用[资料卡片模板](../90-模板/资料卡片模板.md)，为每个可复用结论建立 `CARD-*`。一张卡片只围绕一个主题或一个决策，必须包含证据位置、适用环境、可执行步骤和限制。

## 7. 设计最小实验

为每张需要验证的卡片建立 `EXP-*` 记录：

- 只验证一个关键假设。
- 使用最少的对象、材质和参数。
- 明确 Unity 版本、渲染管线、平台和 MCP 能力。
- 明确成功、部分成立和失败的判定条件。
- 预先决定要保存的截图、日志、参数和性能数据。

## 8. Unity/MCP 验证

在隔离测试场景中执行实验。MCP 负责可重复的对象和参数操作，Unity 负责运行和呈现结果；运行日志、截图和性能数据作为证据保存。

如果 MCP 不支持某项操作，记录具体能力限制，并使用 Editor 脚本、预制模板或人工操作完成对照实验。不能把“工具没做出来”误判为“技术方案不可行”。

## 9. 结果判定

实验结果分为：

- **支持**：关键结论在目标环境中复现。
- **部分支持**：只在特定版本、参数或场景下成立。
- **不支持**：结果与结论明显冲突。
- **无法验证**：缺少资源、环境或工具能力，原因已记录。

更新知识卡片的结论、限制和可信度，不修改原始资料内容。

## 10. 沉淀

根据结果选择落点：

- 通用原则：更新解释或参考文档。
- 可操作步骤：更新教程或操作指南。
- 可复用参数：建立材质、Shader、Prefab 或参数模板。
- 具体效果方案：更新 `effects/` 下的需求和复盘。
- MCP 经验：更新 MCP 能力验证清单或自动化脚本说明。

同时在 `knowledge/index.md` 建立资料、卡片、实验和效果/资产之间的追踪关系。

## 11. 复核和淘汰

当 Unity、渲染管线、插件或目标平台变化时，重新检查受影响卡片。链接失效、版本过期或结论被替代的资料进入 `archived` 或 `deprecated`，保留原因和替代来源。

## 失败处理

- 来源不明：保留在 `inbox`，不进入知识卡片。
- 授权不清：只保存元数据和引用，不保存本地副本。
- 文件损坏：记录校验失败，等待重新获取。
- 版本不兼容：建立隔离实验，不把结果推广到当前项目。
- 无法复现：记录缺失依赖和工具限制，状态保持 `experimental` 或 `无法验证`。
